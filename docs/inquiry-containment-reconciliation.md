# Public inquiry confirmation controls

The public inquiry handler verifies Cloudflare Turnstile server-side before any modern inquiry lookup or write. Siteverify must return success, its hostname must match the request origin and any submitted hostname selector, and its action must be `public_inquiry`. A deduplicated inquiry does not send another confirmation or create another lead/follow-up.

Before Resend, the handler atomically reserves the email allowances in `reserve_inquiry_confirmation_quota`: one attempt per normalized recipient in a rolling 24 hours and up to 50 attempts per project in a rolling 24 hours. A reservation is retained when the provider fails or times out. If a verified client IP is available, the same RPC applies the existing ten-attempt per-IP rolling 24-hour sub-limit. An absent or untrusted IP skips only that sub-limit; the recipient and project controls still apply and the inquiry remains eligible for delivery. Database or quota errors suppress the email without undoing the saved lead and follow-up.

B1 lead limits are separate from confirmation-email limits. `project_public_inquiry_limits` stores each project's cap and rolling window. The migration gives existing and new projects 100 new public inquiry leads per rolling 24 hours. A `BEFORE INSERT` trigger on `public.leads` takes a project-scoped transaction lock and counts all recent `source='public_inquiry'` leads for that project across phases, hostnames, and entry modes, including the legacy adapter. It rejects before the lead and follow-up transaction can commit. Existing idempotency references bypass the count and reuse their lead/follow-up.

`SUPABASE_GATEWAY_IP_HEADER_VERIFIED=true` is required before the handler uses `CF-Connecting-IP` for that optional IP quota. [Supabase documents that its managed platform sets this header](https://supabase.com/docs/guides/api/query-plans), and [Cloudflare documents it as a client-IP header](https://developers.cloudflare.com/fundamentals/reference/http-headers/). Neither source confirms that Supabase ingress overwrites a client-supplied value of the same name. That overwrite behavior has not been established, so leave this setting unset and treat the header as untrusted. The handler never uses `X-Forwarded-For`; an untrusted address skips only the IP sub-limit and remains eligible for delivery.

`PUBLIC_INQUIRY_CONFIRMATIONS_ENABLED` remains off by default outside staging, and `SUPPRESS_OUTBOUND_EMAILS=true` is an independent kill switch. On the exact staging project `kvocwmrcuhiaezlcgzjf`, sending defaults on unless `PUBLIC_INQUIRY_CONFIRMATIONS_ENABLED=false`, but only recipients whose SHA-256 address hash is in the code or `STAGING_PUBLIC_INQUIRY_RECIPIENT_HASHES` can reach Resend. The code allowlist contains the hash of the one approved controlled inbox; the raw address is not stored in source or evidence. The allowlist runs before the quota reservation and before any Resend request.

`20261120002343_inquiry_confirmation_email_quota.sql` is the original quota migration already applied in production; preserve its file and ledger identity. Slice B adds a forward-only migration and does not change production. Apply hosted changes only to the explicitly authorized staging project, after comparing its schema and migration ledger.

## Legacy live-form compatibility

The exact seven-field request from `90b3c86` is accepted only while the server-side compatibility flag is on and the Wamule tenant/project/phase settings resolve to an active owned scope. The flag defaults on only on the exact staging project (Wamule tenant `wamule`, project `wamule`, phase `default`); a staging override to another scope disables the adapter. Production and other projects require explicit `WAMULE_LEGACY_INQUIRY_COMPAT_ENABLED=true`. Legacy requests use the same Postgres lead allowance as all other inquiry modes, save the lead and staff follow-up atomically, and never send confirmation email. A log event records each use without contact details. Turn the flag off and remove the adapter only after the upgraded production inquiry form is verified to send valid Turnstile tokens for its configured hostname and action. See [legacy-public-inquiry-adapter.md](legacy-public-inquiry-adapter.md).

## Verification state

Local mocked handler tests verify invalid challenges, one email across retries with fresh tokens, quota denial, untrusted IP delivery eligibility, the staging recipient allowlist, legacy suppression, and provider failure with the lead/follow-up preserved. The fresh-database Postgres check exercises the migration, role grants, recipient/project/IP limits, concurrency and rolling expiry. These local checks are not hosted staging acceptance.

Staging acceptance still needs a controlled inbox, matching Turnstile site and secret configuration, and the existing Resend credentials/sender configuration. It should record the deployed function version and tested commit, verify one delivery and a retry with no duplicate, and exercise invalid tokens, B1 lead exhaustion, recipient and project email-cap exhaustion, the disallowed-recipient path, an untrusted-IP send, and saved lead/follow-up after a simulated provider failure. Production has not been queried or changed. Automatic buyer confirmations remain planned for production until that separate production verification succeeds.
